# 0.7.0: execution record

This record keeps what happened while 0.7.0 was designed, built and reviewed: the process, the decisions and the rulings
with their reasons, the deviations from the plans, every review finding and what became of it, and the measurements that
changed a decision. It is written for a reader who never saw the working files of the execution; those files are named
here by their role (the research, the designs, the design critiques, the plans, the plan reviews, the plan changes, the
prototype reports, the execution ledgers, the task briefs and reviews, the final reviews, the fix-wave specs and
reports, and the re-reviews), not by their location. It was written after the release, from those files and the git
history; until 0.9.0 they were not kept in the repository.

0.7.0 is two pull requests published by one Release PR: #18, a `fix!:` with six defects of published releases (D1-D6),
merged first, and #20, `feat: extra volumes`, merged second; release-please's Release PR #19 waited for both. Each pull
request had its own design, plan, plan review, execution ledger and final reviews; this record covers both, in that
order, section by section.

Roles: the **owner** of the repository authorized the execution on 2026-10-03 to run without asking, merges and releases
included (the autonomous mode); the **controller** wrote the designs, dispatched every task and review, and ruled on
every finding; an **implementer** applied one task of a plan; a **reviewer** checked one task, a plan or a whole branch,
on copies of the repository.

## What 0.7.0 is

**The fixes (#18).** D1: a map-form file of `configFiles.files` drops every key whose value is `null` or empty (`key:`),
at any depth of nested maps (a list is rendered as written), the same from every values layer on Helm 4.3 and 3.22, and
a `null` file is no file. D5: a `null` entry of `resources.limits` (or of `resources.requests` other than the required
`cpu` and `memory`) and `resources.limits: null` render no such limit or request. D2: `configFiles.mountPath` is
compared normalized (`/tmp`, `/`, and the ServiceAccount token directory while `automountToken` is true fail) and
rendered quoted, as written. D3: an enabled ExternalSecret needs a `data` entry, and the keys an enabled block needs are
`required` (`cronjob.schedule`, `externalSecret.secretStoreRef.kind` and `.name`, `httpRoute.parentRefs`,
`ingress.hosts`). D4: a main-container probe port given by name must be a `ports` name. D6: the entries of
`httpRoute.parentRefs` and `httpRoute.matches` are closed objects with exactly the fields of the Gateway API v1.6.2
Standard CRD ([ADR-0045](../adr/0045-null-in-configfiles-and-resources-is-absent.md),
[ADR-0046](../adr/0046-configfiles-mountpath-compared-normalized-rendered-as-written.md),
[ADR-0047](../adr/0047-when-enabled-keys-required-externalsecret-source-probe-port-names.md),
[ADR-0048](../adr/0048-httproute-parentrefs-and-matches-are-closed.md)).

**Extra volumes (#20).** A component gets `volumes`, a map keyed by the volume name of typed entries (`emptyDir`,
`configMap`, `secret`, `persistentVolumeClaim` for an existing claim, `ephemeral`), each one pod volume and its mount in
the main container; a `null` entry or field is absent in every values layer. The schema closes the fields and guards
check the names, the fields of each type, normalized mount paths, nesting, `readOnly`, sizes, the component's own
objects, one claim per entry, and an existing `ReadWriteOnce` claim on a Deployment (one pod at a time).
`strategy.rollingUpdate: null` is absent, and `rollingUpdate` next to `Recreate` became a guard. The mounted ConfigMaps
and Secrets feed the Reloader annotations
([ADR-0049](../adr/0049-volumes-are-a-map-of-typed-entries-mounted-in-the-main-container.md),
[ADR-0050](../adr/0050-existing-claim-on-a-deployment-and-strategy-rollingupdate-null.md), [upgrade
notes](../upgrading.md#06x--070)).

## The release type: one `fix!:` and one `feat:`, one minor release

- **#18 is `fix!:`** (ruling of 2026-10-05): D1 silently changes the content of a working ConfigMap (every bare key and
  every `null` key of a map-form file is dropped), so it carries `!` and does not ship in a patch: a consumer on a
  `~0.6` range, or a Renovate patch automerge, would get another config file with no render error. The loud fixes
  (values that rendered broken or wider objects now fail) travel in the same pull request; marking them `!` is the
  stricter reading of the repository's rule that an upgrade needing a values change is breaking. This overrode the
  critics' recommendation (`fix:` in a patch with a warning).
- **#18, measured:** lens 2 rendered the six `ci/` scenarios with the published 0.6.0 and with the branch on both Helm
  versions: identical parsed objects; the text differs by one line, `mountPath: "/config"`, in `full` and `job`, so a
  consumer who changes no values gets the same objects and no rollout. With `--reuse-values` the branch's `values.yaml`
  parses to the same data as 0.6.0's. Lens 1 walked an upgrade from the published 0.6.0 for four consumers: each reaches
  a working render by following the upgrade guide. The re-review checked every clause of the squash body on 0.6.0 and on
  the branch, both Helm versions.
- **#20 is `feat:`, not breaking:** it adds `volumes`, accepts one more value of an existing key
  (`strategy.rollingUpdate: null`) and moves one rule from the schema to a guard. The plan review rendered `main`'s
  values with `main`'s chart and the branch (the six `ci/` scenarios, `--reuse-values`, the 11 umbrella-shaped blocks of
  the README, the two e2e umbrellas, both Helm versions): 50 of 50 byte-identical; 24 edge renders changed only where a
  value failed on `main` and now renders. Lens 2: 12 of 12 identical, with `--reuse-values` from `main` and from the
  published 0.6.0 too. The one observable loosening: `helm lint --strict` of chart-base itself exits 0 instead of 1 on
  `rollingUpdate` next to `Recreate` (measured; it prints the guard's message as an INFO line); `helm template` still
  fails. The squash has no body.
- **One release:** release-please 17.6.0 (bundled by the pinned action v5.0.0), source reading: a `BREAKING CHANGE:`
  footer is printed under "⚠ BREAKING CHANGES" whatever the type, only its last text line is kept (so the body is one
  line), and a pre-1.0 minor is cut for any breaking commit or `feat`. Measured after the merges: #19 opened with the
  footer under "⚠ BREAKING CHANGES" after #18, and was regenerated with "Features" after #20.

## Measurements that changed a decision

- **A bare key is a YAML null that works** (the 0.6.1 critique: `grpc:` in an OpenTelemetry Collector file renders
  `grpc: null`; without it the Collector fails its configuration validation, `must specify at least one protocol`,
  measured with `otelcol validate` of 0.162.0): the fix is breaking, and 0.6.1 became 0.7.0's first pull request.
- **A `null` resource quantity is stored as `"0"`** (the 0.12.0 research, kube-apiserver 1.33 and 1.37 with both Helm
  versions: an install rejected with `limit of 0`, or a silent zero limit): D5 joined the fixes.
- **A misspelt key in an `httpRoute` entry widens the route** (the 0.11.0 research: the API drops unknown keys, so
  `pathh: /api` becomes a catch-all and `sectioName` every listener): D6 joined the fixes.
- **release-please 17.6.0 keeps only the last text line of a footer** (source reading of `src/commit.ts`): the squash
  body is one line (0.6.0's was one line too).
- **On Helm 4.3, a `null` of the umbrella's own values is ignored while nothing is passed for the alias, and four
  required keys then keep a default that fails the schema** (the plan review: `minLength: got 0, want 1` or `minItems:
  got 0, want 1` on Helm 4.3.0, `missing property` or `'allOf' failed` on 3.22.0): the consumer null table got a row of
  its own and an alias-contract check.
- **A mutation that breaks a scenario's render makes helm-unittest rewrite the snapshot file** (the prototype and the
  plan review: `Snapshot: 24 passed, 24 total`, the file changed): every mutation block restores the snapshots and every
  commit block refuses a changed snapshot.
- **The private-data grep matched `api:\n` inside quoted test strings** (the plan review: 12 false positives): the
  drive-letter pattern is anchored at a word boundary and the plans expect `CLEAN` again.
- **A JSON round trip loses integers above 2^53** (the plan review: `--set ...=9007199254740993` renders `...992`
  through one, and passes every unit test): the design had chosen an in-place `chart-base.pruneNulls` on a deep copy for
  this reason, and the alias contract gained a check that pins it.
- **Through an umbrella, a `null` from `-f` or `--set` that deletes a required key passes `helm lint` on both Helm
  versions, and Helm 4.3 lints no subchart schema when the umbrella has no `templates/`** (lens 1 of the fixes): the
  documents no longer say the required keys "fail `helm lint` too"; the rule was corrected for later designs as well.
- **A `null` field inside a route entry worked on Helm 3.22 and is refused by Helm 4.3** (lens 2 of the fixes,
  kube-apiserver 1.33.0 and 1.37.0 with the v1.6.2 Standard CRDs: a plain create drops the `null`, a server-side apply
  rejects it): the upgrade guide, ADR-0048 and the squash body list it among the values that now fail.
- **The strategy transitions** (before the volumes prototype, kube-apiserver 1.33.0 and 1.37.0, Helm 4.3.0 and 3.22.0):
  T1 (no `strategy` → `{type: Recreate}`) is rejected on Helm 4.3 only (`spec.strategy.rollingUpdate: Forbidden`, the
  server-defaulted `rollingUpdate` owned by no field manager) and accepted with `--server-side=false`; T2 (→
  `RollingUpdate` with `maxSurge: 0`, `maxUnavailable: 1`) is accepted on both: the stop condition was not met, and the
  claim guard's remedies are the measured ones. Lens 2 of the volumes measured `{type: RollingUpdate}` → `{type:
  Recreate}`: rejected on Helm 4.3.0, accepted on 3.22.0.
- **Helm's schema library reports a `propertyNames` failure at an unrelated path**: volume names are checked by a guard.
- **A YAML 1.1 key is renamed** (the volumes prototype: a volume key `y` renders `"true"`): documented next to
  `volumes`.
- **`rollingUpdate` next to `Recreate` as a guard** (both Helm versions: `helm lint --strict` of chart-base itself exits
  1 before and 0 after, `helm template` fails in both): the upgrade notes and ADR-0050 say so.
