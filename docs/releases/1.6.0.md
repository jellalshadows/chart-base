# 1.6.0: a StatefulSet workload type with a claim per pod

1.6.0 adds `workload.type: statefulset`, the optional `statefulset` block and the `volumeClaimTemplate` volume type.
Values that render on 1.5.0 render the same manifest, with the same guards and messages. The only exceptions are two
schema messages, for `workload.type` and a volume `type`, which now list the new values.

## What changed

- **A StatefulSet `<release>-<alias>`** ([ADR-0071](../adr/0071-a-statefulset-workload-type-with-a-claim-per-pod.md),
  amending ADR-0008, 0015, 0036, 0037, 0038, 0049, 0050, 0056, 0057 and 0062).
  - It keeps the frozen selector labels.
  - `serviceName` is set when `service.enabled`.
  - `replicas` is left out while the HPA or KEDA is on.
  - It uses the Deployment's pod template, with the Reloader annotations and the config checksums.
- **The Service is headless:** the component's one Service keeps its name and gets `clusterIP: None`, so each ready
  pod has a DNS name.
- **`volumes.<name>.type: volumeClaimTemplate`:** one PersistentVolumeClaim per pod, which outlives the pod.
  - Its template carries only the two selector labels. The API refuses any change to `volumeClaimTemplates`, so
    `commonLabels` there would fail every upgrade that changes them.
- **`statefulset`:**
  - `podManagementPolicy`;
  - `updateStrategy` (`RollingUpdate` with `partition`, or `OnDelete`);
  - `persistentVolumeClaimRetentionPolicy` (absent: Retain).
- **`updateStrategy` is always rendered,** with the Kubernetes defaults written out, so Helm owns its keys and a switch
  to `OnDelete` takes one upgrade.
  - `maxUnavailable: 1` is written only from Kubernetes 1.37, where the API server defaults it.
  - Below 1.37 the API server drops that field, so writing it there would leave a permanent rendered-vs-live diff.
- **As on a Deployment:**
  - routes and Ingress;
  - the HPA and KEDA, with the handover;
  - the PDB;
  - the monitors;
  - the preStop sleep;
  - the default topology spread, keyed on `controller-revision-hash`.

  `strategy` and `progressDeadlineSeconds` are ignored.
- **Guards:**
  - a `statefulset` member on another workload type;
  - `rollingUpdate` next to `OnDelete`;
  - a `NodePort` or `LoadBalancer` Service;
  - a `volumeClaimTemplate` outside a StatefulSet;
  - an existing `ReadWriteOnce` claim with more than one replica or an autoscaler;
  - a name longer than 52 characters.

## Evidence

- **Unit tests:** 1721 (139 new), written test-first, unit by unit. The 1.5.0 suite passes 1581 of 1582 against the
  1.6.0 templates; the one failure used `statefulset` as its example of an unknown type.
- **e2e on kind 1.33 and 1.37:**
  - two Ready pods behind the headless Service;
  - one Bound claim per pod, and a pod's claim outlives the pod;
  - the switch to `OnDelete` in one upgrade, which leaves `spec.updateStrategy` without `rollingUpdate`.

  The `full` release still has 18 objects.
- **Independent verification:** no blocker; 6 of 6 claims pass on Helm 4.3.0 and 3.22.0.
  - Values that 1.5.0 renders give byte-identical output: 198 cases × 6 pairs, in the normal shape and in the
    `--reuse-values` shape from 1.0.0 and 1.5.0.
  - Rejections are unchanged apart from 8 intended probes.
  - The fields a StatefulSet cannot change stay byte-identical across 20 routine changes, including the chart version
    and the namespace.
  - kubeconform: 72 of 72 renders valid.
  - The contract went from 689 keys to 698; none was removed.
- **Native review**, in six slices, because the whole change exceeded one reviewer's context:
  - five slices were approved;
  - the last was under the review budget;
  - two warnings led to changes before the merge: the 1.37 `maxUnavailable` default and the diff below 1.37.
