# 0.6.0: execution record

This record keeps what happened while 0.6.0 was designed, built and reviewed: the process, the decisions and the rulings
with their reasons, the deviations from the plan, every review finding and what became of it, and the measurements that
changed a decision. It is written for a reader who never saw the working files of the execution; those files are named
here by their role (the research, the design, the plan, the plan review, the plan changes, the prototype report, the
execution ledger, the task briefs and reviews, the hardening spec and report, the documentation amendment spec and
report, the final reviews, the fix-wave spec and report, and the re-review), not by their location. It was written after
the release, from those files and the git history; until 0.9.0 they were not kept in the repository.

Roles: the **owner** of the repository approved the design (decisions 1-3) and the plan review's points (decisions 4-7)
on 2026-10-03, and then authorized the execution to run without asking, merges and releases included (the autonomous
mode; 0.6.0 is the first release executed under it); the **controller** wrote the design from the research, dispatched
every task and review, and ruled on every finding; an **implementer** applied one task of the plan; a **reviewer**
checked one task, the plan or the whole branch, on copies of the repository.

## What 0.6.0 is

A component can run as an existing ServiceAccount (`serviceAccount.name`: only with `create: false`, a DNS-1123
subdomain of at most 253 characters, never `default`, rendered quoted), and its pods' ServiceAccount gets namespaced
RBAC: `rbac.rules` renders a Role and a RoleBinding `<fullname>`, and `rbac.clusterRoles` renders one RoleBinding
`<fullname>.<ClusterRole>` per existing ClusterRole. Every RoleBinding binds the pods' ServiceAccount in the release
namespace, with `roleRef.apiGroup` always rendered; on a `job` component the Role and the RoleBindings are hooks of the
Job's phase (weight `-10`, `before-hook-creation,hook-succeeded`). The schema rejects `*` in every rule list, in
`resourceNames` and as a ClusterRole name, takes the twelve standard verbs only, no `nonResourceURLs` and no empty list.
Guards, each with its remedy, reject RBAC bound to the namespace's `default` ServiceAccount, RBAC without
`serviceAccount.automountToken: true` (unless no ClusterRole is bound and `use` is the only verb of every rule), the
ClusterRole `cluster-admin`, `deletecollection` with `resourceNames`, `create` on a resource with `resourceNames` when
the same rule grants neither `patch` nor `update`, `serviceAccount.name: default`, `serviceAccount.name` with `create:
true`, and `serviceAccount.annotations` with `create: false` (the breaking change). The release also records that a
guard fails `helm template`, install and upgrade but not `helm lint`
([ADR-0042](../adr/0042-existing-serviceaccount-and-namespaced-rbac.md),
[ADR-0043](../adr/0043-job-component-rbac-is-a-hook.md),
[ADR-0044](../adr/0044-guards-fail-the-render-helm-lint-reports-them.md), [upgrade notes](../upgrading.md#05x--060)).

## The release type: `feat!:`

- **The breaking case:** `serviceAccount.annotations` together with `serviceAccount.create: false`, which 0.5.0 silently
  ignored (no ServiceAccount is created to carry them), now fail the render. The plan review's point (b) recommended
  `feat!:` because the repository's own rule (`docs/upgrading.md`, `docs/README.md`) makes a release whose upgrade needs
  a values change breaking; the owner chose it (decision 5). The precedent is 0.3.0 (`0cb0da7`, a squash with a `feat!:`
  subject and a `BREAKING CHANGE:` body, listed under "⚠ BREAKING CHANGES"). The prototype had kept `feat:` with 0.4.1
  as the precedent (judgment call 7, superseded).
- **Byte identity, measured:** the six `ci/` scenarios of `main` render the same manifests with the final chart on Helm
  4.3.0 and 3.22.0 (the prototype's replay). Lens 1 rendered them with the published 0.5.0 (pulled anonymously) and with
  the branch: identical. Lens 2 rendered them on both Helm versions and both Kubernetes versions: 24 of 24 identical;
  with `create: false`, `automountToken: true` or both added, 32 of 36 identical, and the 4 others are the `full`
  scenario, which sets `serviceAccount.annotations`, with `create: false`: the breaking guard.
- **`--reuse-values`, measured:** rendering the final chart with an earlier release's `values.yaml` (what Helm's
  `--reuse-values` renders with) gives, on both Helm versions, `missing property 'rbac'` from 0.5.0; `missing properties
  'rbac', 'networkPolicy'` from 0.4.1 and 0.4.0; `missing properties 'rbac', 'metrics', 'prometheusRule',
  'networkPolicy'` from 0.3.0; and from 0.2.0 the same plus `'enableServiceLinks'` and `'/cronjob': missing property
  'suspend'`. Lens 2 ran real upgrades of a 0.5.0 install on API servers (Helm 4.3.0 on 1.33.0, Helm 3.22.0 on 1.37.0):
  `--reuse-values` fails with `missing property 'rbac'`; `--reset-then-reuse-values` upgrades to a manifest identical to
  the 0.5.0 revision; the breaking case fails with the guard's message, an override `annotations: {}` still fails, and
  `annotations: null` upgrades to a manifest identical to the 0.5.0 revision.
- **The version:** `release-please-config.json` has `bump-minor-pre-major: true`, so `feat!:` on 0.5.0 gives 0.6.0 (lens
  2). The squash body is lens 2's footer, one paragraph on one line.

## Measurements that changed a decision

- **A name-restricted `create` is honored for a server-side apply and for a create through an update** (the Task 3
  review, kube-apiserver 1.33.0 and 1.37.0: an apply of an absent ConfigMap is 201 with `[get, patch, create]` and 403
  with `[get, patch]`; a PUT that creates an absent Lease is 201 with `[get, update, create]` and 403 with `[get,
  update]`; a POST is 403): the guard approved with the design rested on "such a rule never matches", and was narrowed
  to rules with neither `patch` nor `update`.
- **`<fullname>-<ClusterRole>` collides across aliases** (the prototype, Helm 4.3.0 and 3.22.0: aliases `api` with
  `clusterRoles: [view]` and `api-view` with `rules` both render `RoleBinding/vending-api-view`): the owner chose
  `<fullname>.<ClusterRole>` (decision 4). Revision 1 measured that `vending-chart-base.view` and
  `vending-chart-base.system:aggregate-to-view` are created and take effect on kube-apiserver 1.33.0 and 1.37.0.
- **A same-name ServiceAccount handover in one step breaks silently** (the plan review and revision 1, real `helm
  upgrade` with Helm 4.3.0 and 3.22.0 on both API servers: the upgrade reports `deployed`, Helm deletes the
  ServiceAccount, the Deployment does not roll, a new pod is rejected with `serviceaccount "r-chart-base" not found`;
  with `helm.sh/resource-policy: keep` deployed first, the ServiceAccount is kept with the same UID): the two-step
  handover is documented (decision 6).
- **Helm deletes a hook ServiceAccount whatever `helm.sh/resource-policy` says** (lens 2: a minimal chart whose only
  hook is a ServiceAccount with `keep`, Helm 4.3.0 and 3.22.0 on kube-apiserver 1.33.0 and 1.37.0: gone after the
  phase): the two-step handover holds for `deployment` and `cronjob` components only; a `job` component's procedure is
  one step.
- **`helm lint` does not fail on a guard** (the hardening review, Helm 4.3.0 and 3.22.0: lint turns `fail` into an INFO
  line and exits 0, for every guard of the chart since 0.1.0): ADR-0044, and every document that said otherwise was
  corrected.
- **Through an umbrella, `helm lint` misses a `null` from `-f` that deletes a required key** (Task 5b, then lens 1 and
  the fix wave on both Helm versions: lint exits 0, `helm template` fails; from the umbrella's own `values.yaml` Helm
  3.22.0 rejects it in lint and template alike and Helm 4.3.0 ignores the `null`, the chart's default staying): ADR-0027
  was amended by ADR-0044.
- **An override `serviceAccount.annotations: {}` is merged and clears nothing; `null` clears them** (the plan review,
  both Helm versions): the guard's message and the upgrade note name `null`.
- **The schema's `not` reports only `'not' failed`** (both Helm versions): `serviceAccount.name: default` and
  `cluster-admin` became guards with messages (judgment call 3).
- **`create` by name on a subresource is honored** (`can-i create pods/<name> --subresource=exec` and `create
  serviceaccounts/<name> --subresource=token` answer yes by name on both API servers): the `create` guard checks
  resources without a `/` only (judgment call 2).
- **RBAC names have no length limit** (a 312-character RoleBinding is created on both API servers; lens 2 created
  RoleBindings of 254 and 664 characters): no length guard for binding names (judgment call 1).
- **A test and the alias contract could not tell the subject's namespace from the release name** (the Task 2 review: a
  `.Release.Name` mutant passed 176 of 176 tests; the Task 4 review and the hardening wave: the alias contract passed
  with that mutant on both Helm versions): one test renders in the namespace `"123"`, and the alias contract renders in
  the namespace `platform`.
- **`kubectl auth can-i` answers `no` with a warning for a misspelt verb** (the hardening wave, real kubectl against
  kube-apiserver 1.33.0 and 1.37.0: `Warning: verb 'delte' is not a known verb`): the e2e's `can_i` treats that warning
  as an error, as it already did for an unknown resource type.
- **Without `--namespace`, Helm takes `HELM_NAMESPACE`, then the kubeconfig context's namespace, and `default` only when
  neither is set** (the fix wave, both Helm versions): the documents that said "`default`" say so.

Made when the plan was prototyped; call 13 was added in revision 1. The plan records a reason for each; it names no cost
if wrong.

| # | Call | Why (as recorded) |
|---|---|---|

| 10 | The pod's `serviceAccountName` is quoted only when it comes from `serviceAccount.name` | existing values render byte-identical manifests; an existing ServiceAccount may be named `on` or `true` |
| 11 | ADR-0042 (the contract) and ADR-0043 (the job's RBAC as hooks, amending ADR-0007 and ADR-0041); no workflow change; README regenerated in Task 5 only | ADR-0043 amends ADR-0041 because a failed hook creation does not delete the hooks created before it (Helm's `execHook` returns at once); `ci.yaml` runs `e2e.sh` as it is |
| 12 | `*` rejected in `resourceNames` too | it is no wildcard there and would silently allow nothing (`ResourceNameMatches` compares literally) |
| 13 | `*` rejected as a ClusterRole name (plan review N1) | a `roleRef` reads it as a name and would bind a ClusterRole literally named `*` |
