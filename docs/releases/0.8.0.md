# 0.8.0: execution record

This record keeps what happened while 0.8.0 was designed, built and reviewed: the process, the decisions and the rulings
with their reasons, the deviations from the plan, every review finding and what became of it, and the measurements that
changed a decision. It is written for a reader who never saw the working files of the execution; those files are named
here by their role (the research, the design, the design critique, the plan, the plan review, the plan changes, the
prototype report, the execution ledger, the task briefs and reviews, the final reviews, the fix-wave spec and report,
and the re-review), not by their location. It was written after the release, from those files and the git history; until
0.9.0 they were not kept in the repository.

Roles: the **owner** of the repository authorized the execution on 2026-10-03 to run without asking, merges and releases
included (the autonomous mode); the **controller** wrote the design, dispatched every task and review, and ruled on
every finding; an **implementer** applied one task of the plan; a **reviewer** checked one task, the plan or the whole
branch, on copies of the repository.

## What 0.8.0 is

A component gets `initContainers` and `sidecars`: two maps keyed by the container name, rendered into the pod's
`spec.initContainers` in one start order (`order` from -1000 to 1000, defaults 0 for an init container and 1000 for a
sidecar; on a tie an init container first, then by name), every sidecar a native sidecar (`restartPolicy: Always`). In
these maps a `null` entry or optional field is absent at any depth (a list is kept as written); inside an env variable's
`valueFrom` or a probe's `httpGet` or `exec`, and in a required field, it stays a schema error. Each entry starts from
the chart's hardened security context and merges its own over it, never from the component's `securityContext`; nothing
else comes from the main container except through `inheritEnv: true` and explicit `volumeMounts`. Sidecars get
pod-internal `ports` and closed `probes`. Guards, each with its remedy, check the names, the Kubernetes list form and
`restartPolicy`, UID 0 with `runAsNonRoot: true` on the merged context, a `job` or `cronjob` with a sidecar (it needs
`job.activeDeadlineSeconds`), env literals and duplicate names, port names and numbers in the pod, a sidecar probe's
port name, and every mount per container. `volumes.<name>.mountPath` becomes optional for a volume another container
mounts. The entries' env references feed the Reloader, and with a sidecar the HPA's built-in targets measure the main
container ([ADR-0051](../adr/0051-init-containers-and-sidecars-are-two-maps-in-one-start-order.md),
[ADR-0052](../adr/0052-hpa-targets-measure-the-main-container-with-sidecars.md), [upgrade
notes](../upgrading.md#07x--080)).

## The release type: `feat:`, not breaking

- **Byte identity, measured:** with the final chart against `main`'s, on Helm 4.3.0 and 3.22.0, the six `ci/` scenarios,
  `--reuse-values` from `main`, the shared test values and the 14 values blocks of `main`'s README recipes render the
  same bytes (the prototype's replay). The plan review: 64 of 66 renders identical; the other two are one incomplete
  README overlay that fails alone on both charts with the same errors in another order, and renders identically when
  applied as the overlay it is. Lens 2: 11 inputs, 0 differences on both Helm versions (the six scenarios by `main`, by
  the branch and by the branch with 0.7.0's `values.yaml`, and the five shared test values).
- **`--reuse-values`, measured with real upgrades:** lens 2 installed the published 0.7.0 on kube-apiserver 1.37.0 and
  upgraded with `--reuse-values` to the branch for `ci/deployment`, `ci/cronjob` and a CRD-free "core-full" (HPA, env
  references, a tmpfs volume, a ConfigMap item, a config file): `helm get manifest` byte-identical before and after, on
  Helm 4.3.0 and 3.22.0. (Observation: `--reuse-values --set sidecars.shipper=null` leaves the sidecar in place on both
  versions, because Helm turns the old values into the defaults; the upgrade guide already tells direct installs not to
  use `--reuse-values`.)
- **Values that failed on `main` still fail;** two of them with another message (a volume without `mountPath`, and an
  `emptyDir` or `ephemeral` volume mounted read-only by every container). The first moved from the schema to a guard:
  `helm lint --strict` of chart-base itself exits 0 on it instead of 1 (it prints the guard as an INFO line), while
  `helm template` still fails (measured on both Helm versions; the upgrade notes and ADR-0051 say so).
- **The squash body** is one prose line that names the HPA change, with no conventional type at its start, no `: `, no
  `#` and no `BREAKING`: by release-please v17.6.0's commit parser (source reading of `splitMessages`, the footer tokens
  and the breaking detection in `src/commit.ts`), one `feat` commit and no breaking note. The published CHANGELOG has
  "Features" only.

## Measurements that changed a decision

- **A `ContainerResource` HPA is created and changed in place both ways** (before the prototype: kube-apiserver 1.33.0
  and 1.37.0, Helm 4.3.0 server-side and 3.22.0, 20 steps, each exit 0, the stored `spec.metrics` exactly the rendered
  list): decision 13 stands as designed. Lens 2 repeated it through real upgrades (add a sidecar, remove it).
- **`httpGet.host` and `tcpSocket.host` on a probe are admitted on 1.33.0 and rejected on 1.37.0** (Pod Security
  `restricted`, `probe or lifecycle host`): the sidecar probes are a closed definition without `host`; the main
  container's stay open (owner question O2, left for the 1.0 contract freeze).
- **The native sidecar shape is admitted under Pod Security `restricted`; a probe on a plain init container is refused
  by the API** (both API servers): the plan's shapes; probes on sidecars only.
- **A repeated `env` name fails the install on Helm 4.3.0** (server-side apply: `.env: duplicate entries for key
  [name="POD_NAME"]`) **and is created with a warning on Helm 3.22.0**: with `inheritEnv: true`, a name the component
  also has fails the render; ADR-0051 states the measurement.
- **`mergeOverwrite` keeps an empty list** (`capabilities: {drop: []}` renders `drop: []`, the default's `[ALL]` is not
  kept; Pod Security `restricted` then rejects the pod): documented, not guarded (judgment call 3).
- **helm-unittest decodes the rendered manifests as YAML 1.2** (a quoting test with `yes` or `no` passes with the value
  unquoted: measured): the quoting tests use `true`; the Task 1 review found a `command: ["no"]` test that asserted
  nothing.
- **helm-unittest hands a `set` number as a `float64`, Helm's `--set` as an `int64`**: the mixed `order` case is checked
  by the alias contract, not the unit suite (judgment call 7).
- **The first error line of a failing render varies between runs** (revision 1: 12 runs of each RED state; the first
  line varied for 50 failures, the set of lines for none): a RED expectation lists every error line of a multi-error
  failure.
- **A volume without `mountPath` moved from the schema to a guard** (plan review S3: `helm lint --strict` of chart-base
  itself exits 1 on `main` and 0 on the branch, `helm template` 1 on both): the upgrade notes and ADR-0051 say so.
- **GitHub search matches nothing for an unquoted `chore(main):`** (lens 2 and the re-review, read-only `gh` queries
  against the merged 0.7.0 Release PR #19: the unquoted forms return nothing, the quoted phrase returns #19): the
  release runbook and Task 11 quote the title.
- **agnhost 2.66.1's `netexec` answers `/healthz` with 412 until a UDP or SCTP server runs** (the first CI run's log and
  `netexec.go` at that version): the e2e's fronting-recipe application gets a UDP port.
- **An explicit `gh pr merge --subject` gets no ` (#N)` from GitHub** (seen at the merge): the 0.8.0 CHANGELOG line
  links the commit only; later merges pass the number in the subject.
- **YAML 1.1 renames keys** (measured on both Helm versions: two unquoted sidecar keys `on` and `yes` render one
  container `"true"`; `off`, `Off`, `OFF` and `n` become `"false"`, while `oFF` is kept; a main `env` name `OFF` renders
  `"false"`; `config: {OFF, ON, N}` collides silently): the values comments name the spellings and say to quote them.
- **A `null` inside a list is kept** (lens 2 and the re-review: `securityContext.capabilities.add: [NET_BIND_SERVICE,
  null]` renders the `null`): every document says a list is kept as written.
- **A sidecar's own `runAsUser` and `runAsGroup` render next to the pod's** (lens 1): no document says "one UID and GID
  for the pod" any more.

## Controller decisions (the design)

| # | Decision | Why |
|---|---|---|
| 1 | `feat:`, not breaking, one PR released alone as 0.8.0; the squash body is one line that names the HPA change, with no `BREAKING CHANGE:` footer and no conventional type at its start | it adds two keys and no required one; every values file that renders on `main` renders the same (measured) |
| 2 | Two maps, one start order, `null` absent: DNS-1123 names unique across both maps and the main container; `order` -1000..1000, defaults 0 and 1000, on a tie the init container first, then the name; the sort key's offset is the schema's minimum; `restartPolicy` is the chart's; a `null` is absent at any depth except inside the definitions shared with the main container | init containers keep their classic meaning and the cheapest effective request; a migration that needs a database proxy is written with `order`; with sidecars at 1000 by default, sequenced init containers do not land behind every sidecar. Cost if wrong: the rule cannot change later without breaking |
| 3 | Each entry's security context is the chart's hardened default merged with its own override, never the component's `securityContext`; a `null` field restores the default | a relaxation made for the main container must not travel silently to sidecars (ADR-0013); the roadmap said "inherit the chart's securityContext", read as "the chart's default". Cost if wrong: a consumer who changes the context for all containers on purpose repeats it per entry. The controller marked this the ruling it was least sure matches the owner's intent |
| 4 | Nothing is inherited from the main container; what the pod grants is shared: `env` references only, `inheritEnv: true` gives exactly the main container's `envFrom` and `env` (a name it would repeat fails), `volumeMounts` keyed by the volume name, nothing mounted automatically; ConfigMap, Secret, `config-files` and `ReadOnlyMany` mounts read-only | least privilege: a log shipper must not get every application secret |
| 5 | Curated, closed entries (`image`, `command`, `args`, `env`, `inheritEnv`, `resources` with required requests, `securityContext`, `volumeMounts`, `order`; sidecars also `ports` and `probes` with a new closed `definitions.probe`); no `lifecycle`, literal env or raw containers | a sidecar probe without `host` and without misspelt fields; the main container's probes stay open (owner question O2) |
| 6 | A sidecar's ports are pod-internal (not in the Service, not a metrics or NetworkPolicy target); a fronting proxy is a README recipe that requires `networkPolicy.enabled: true` and probes by number | per-port exposure can be added later without breaking; without a NetworkPolicy the recipe would be fail-open (critique) |
| 7 | Guards with remedies: the list form and `restartPolicy`; port names and numbers unique in the pod; a sidecar probe's port name among its own ports, and a clause naming where a name is declared (the main container's message too); mounts per container; env literals and duplicates; a `job`/`cronjob` with a sidecar needs `job.activeDeadlineSeconds`; UID 0 with `runAsNonRoot: true` on the merged context | a sidecar that cannot start is restarted for ever and the batch pod never fails; the kubelet resolves a probe's port name in the probed container only (source reading) |
| 8 | The Reloader lists gain the entries' own `secretKeyRef`/`configMapKeyRef` names. With a non-null sidecar, the HPA's built-in targets render as `ContainerResource` metrics of the main container (decision 13, owner question O3 adopted) | 0.8.0 is the first release that allows sidecars with an HPA, so it fixes what the percentage means: pod-wide utilization is diluted by the sidecar's requests. Cost if wrong: changing it later is breaking for components with sidecars and an HPA |
| 9 | The e2e: `deployment` (the start order, a volume an init container fills), `job` (a hook Job with a sidecar completes), the fronting recipe in the NetworkPolicy umbrella, `full` (the stored HPA); the docs: ADR-0051 (amends ADR-0049), ADR-0052, README decisions and two recipes, the guides, `0.7.x → 0.8.0`, the roadmap | the first real run is CI's |
| 10 | Autonomous mode: Task 11 pushes and watches CI; the controller merges, merges the Release PR and verifies the publish | the owner's authorization |

Calls of the design's reviser, kept in the plan and recorded for the owner's review: a `null` stays a schema error
inside the objects whose schema is shared with the main container (an env variable's `valueFrom`, the probe handlers),
the conservative option where the critique's amendment met 0.9.0's single env definition; `readOnly: true` on an
`emptyDir` or `ephemeral` volume is allowed when another container writes it and fails when every mount is read-only; a
main-container probe may not name a sidecar's port.

Left open for the owner, not changed: the main container's probes stay an open object (they accept `httpGet.host`, which
1.37 rejects under Pod Security and 1.33 admits); a `subPath` that matches no `items[].path` is checked for init
containers and sidecars but not for the main container (it would fail values that render today): both are candidates for
the 1.0 contract freeze. Recorded, not built: a `lifecycle` `httpGet.port` by a name the container does not declare (a
`preStop` hook then only produces a `FailedPreStopHook` event: kubelet source reading); a claim's `subPath` file beneath
a ConfigMap mount (loud at container start); `drop: []` in a security context (Pod Security `restricted` rejects the
pod: loud).
