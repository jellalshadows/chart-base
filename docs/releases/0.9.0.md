# 0.9.0: execution record

This record keeps what happened while 0.9.0 was designed, built and reviewed: the process, the decisions and the rulings
with their reasons, the deviations from the plan, every review finding and what became of it, and the measurements
that changed a decision. It is written for a reader who never saw the working files of the execution; those files are
named here by their role (the design, the design critique, the plan, the plan review, the plan changes, the prototype
report, the execution ledger, the task reviews and the final reviews), not by their location.

Roles: the **owner** of the repository authorized the execution on 2026-10-03 to run without asking, merges and
releases included (the autonomous mode); the **controller** wrote the design, dispatched every task and review, and
ruled on every finding; an **implementer** applied one task of the plan; a **reviewer** checked one task, the plan or
the whole branch, on copies of the repository.

## What 0.9.0 is

A component's ExternalSecret (still one per component, with one Secret `<fullname>-secrets`) gains `dataFrom` (External
Secrets' own list, limited to `extract` and `rewrite`, closed at every level), `data` entries that may be `null` and
take `version` and `decodingStrategy`, a curated `template` (`data` and `mergePolicy`, `Merge` by default, required), a
required switch `envFrom` (the Secret injected whole or not), and a file mount (`mountPath`, `items`, `defaultMode`:
the read-only volume `external-secret`, which init containers and sidecars can mount too). `env` gains the
chart-resolved source `externalSecretKeyRef: {key}`, rendered as a `secretKeyRef` on `<fullname>-secrets`. Guards check
the source, the template, the keys while the Secret is injected, the readers with `envFrom: false`, the mount's paths
and keys, and the references, each with its remedy
([ADR-0053](../adr/0053-externalsecret-datafrom-template-files-and-an-envfrom-switch.md),
[ADR-0054](../adr/0054-env-externalsecretkeyref-references-the-components-own-secret.md),
[upgrade notes](../upgrading.md#08x--090)).

## The process

1. **Design** (2026-10-04): the controller wrote the design from a research file (sources, measurements on
   kube-apiserver 1.33.0 and 1.37.0 with the External Secrets 2.11.0 CRDs, and External Secrets v2.11.0's own code run
   in a harness).
2. **Critique** (2026-10-05): three independent critics (consumer, failure modes, roadmap coherence) attacked the
   design, skeptics tried to refute the blocking findings, and a synthesizer wrote the critique: 13 amendments adopted,
   7 proposals rejected, 3 questions for the owner (O1-O3).
3. **Revised design** (2026-10-05): the controller's rulings integrated into the decisions (14 decisions). O1, a
   reference to the component's own Secret in `env`, was adopted and became ADR-0054; O2 (`dataFrom` stays a list) and
   O3 (the name `envFrom` stays) were ruled as the design had them.
4. **Prototype and verified plan** (2026-10-09): the design was prototyped on `main` at `d94f26f` (0.8.0 released) and
   turned into a plan of 9 tasks with the full code, the tests written first, 88 mutations, and every command block.
   A replay applied the plan's blocks to a clean export of `main` and ran every local command block verbatim: the
   final tree was byte-identical to the prototype.
5. **Independent plan review** (2026-10-10): ready with changes, 0 Blocking, 1 Should (S1), 9 Consider (C1-C9).
6. **Revision 1** (2026-10-10): S1 and C1-C9 applied as ruled; 94 mutations (90 unit, 4 alias contract); the replay run
   again with the new counts. Every finding is listed below with where it landed.
7. **Eight tasks**, each implemented on the branch, checked by the replay checker (the tree after each task compared
   with the plan's expected state: 0 differences after every task, re-run by the controller), and reviewed by an
   independent reviewer. The owner paused the run after Task 7 on 2026-10-10; it resumed on 2026-10-11 after the state
   was verified (branch, HEAD, clean tree, nothing running).
8. **Two final reviews** of the whole branch: lens 1, the documents are true; lens 2, the branch as one change (code,
   tests, CI, release readiness).
9. **One final fix wave** (2026-10-11): every finding the task reviews deferred, and the ruled findings of the two final
   reviews, applied in two commits, plus this record. Then a scoped re-review, the push, the pull request and CI.

## The release type: `feat:`, not breaking

- **Byte identity, measured:** the six `ci/` scenarios of 0.8.0, its shared test values and its README recipes render
  the same manifests with 0.9.0 on Helm 4.3.0 and 3.22.0 (the prototype's replay, the plan review: 59 of 60 renders
  identical, the 60th an overlay block that fails alone on both charts, and lens 2: 60 of 60 identical, stdout and
  stderr). The fix wave rendered the six scenarios again after each of its commits: identical on both Helm versions.
- **`--reuse-values`, measured with real upgrades:** the plan review and lens 2 upgraded releases installed from the
  published 0.8.0 on kube-apiserver 1.37.0 with Helm 4.3.0 and 3.22.0. Every direct install upgraded with
  `--reuse-values` fails with `at '/externalSecret': missing properties 'envFrom', 'template'`, whether or not it uses
  `externalSecret`, and the upgrade writes no revision; `--reset-then-reuse-values` upgrades (revision 2 renders 0.8.0's
  manifest byte for byte); umbrellas are not affected. The upgrade guide states this.
- **The precedent:** 0.4.0 (`72ddbc9 feat: Prometheus monitoring (ServiceMonitor, PodMonitor, PrometheusRule) (#10)`)
  and 0.5.0 (`cdf97e1 feat: opt-in NetworkPolicy with sibling-component references (#14)`) added required keys with
  defaults that fail every direct-install `--reuse-values` upgrade the same way, and were `feat:` releases with the
  line documented in the upgrade guide. 0.3.0 and 0.6.0 were `feat!:` for other reasons (a changed default, a
  combination that now fails).
- **Values that failed on 0.8.0:** most still fail, some with another message; three kinds now render (a key of
  `data` that is not a variable name in a disabled or templated-`Replace` block, an `env` name equal to a key of a
  disabled block, and a `null` entry of `data`), the relaxations and the `null` rule that the upgrade guide lists.

## Measurements that changed a decision

- **Through an umbrella, Helm 4.3 drops a `null` of the umbrella's own values while nothing is passed for the alias;
  Helm 3.22 keeps it** (measured on both, the alias contract pins it per version): the docs of `template`,
  `template.mergePolicy` and `envFrom` state the exception, and the alias contract checks every layer.
- **The required keys' `--reuse-values` line** (measured by rendering with each release's `values.yaml`, then with real
  upgrades): the release stayed `feat:` and the upgrade guide gained the 0.9.0 line and the lines of skipped versions.
- **The API server stores every rendered ExternalSecret as rendered** (kube-apiserver 1.33.0 and 1.37.0, External
  Secrets 2.11.0 CRDs, Helm 4.3.0 and 3.22.0), plus the CRD defaults `target.deletionPolicy: Retain` and
  `target.template.engineVersion: v2`: this confirmed that the chart renders no `engineVersion` and that nothing it
  renders is pruned by the API.
- **External Secrets' code in a harness:** `'{{ "production" }}'` renders `production` (the spelling the docs give for
  a constant that must be a key), `data` wins over an extract, and a templated key under `Merge` decodes a base64 text
  of the same name: the constant guard and the documented `b64dec` workaround.
- **Helm's schema library reports a `propertyNames` failure at an unrelated path** (`at '/prometheusRule/enabled'`):
  the tests match the message only, and the variable-name rule became a guard whose message names `envFrom` and the
  remedies instead of a schema rule.
- **`helm lint` of the chart itself with `data.tls.crt`:** exit 1 on 0.8.0 (schema), exit 0 on 0.9.0 (the guard is an
  INFO line under lint): documented in the upgrade guide; the gate stays `helm template`.
- **YAML 1.1 keys** (`on`, `yes`, `Off`, `N`...) arrive as `"true"`/`"false"` and two of them collide: documented, not
  guarded (the chart never sees the original key).
- **A `--set` by index on a list** (helmfile 1.8.0 and Helm, with the list in an umbrella's own values) renders a
  one-entry list: the docs advise varying a remote key in one templated values file. The Task 1 review measured the
  other layout (the list in a `-f` file: the entry is edited in place), and the fix wave re-measured both layouts on
  Helm 4.3.0 and 3.22.0 and on helmfile 1.8.0; the docs now state both.

## Controller decisions (the design)

| # | Decision | Why |
|---|---|---|
| 1 | `feat:`, not breaking, one PR released alone as 0.9.0; the squash body is a second conventional commit for decision 14 | byte identity measured; the `--reuse-values` line as for 0.4.0 and 0.5.0; decision 14 gets its own CHANGELOG line |
| 2 | `dataFrom` is External Secrets' list, limited to `extract` and `rewrite`, closed; `conversionStrategy` next to a non-empty `rewrite` fails | External Secrets' documentation applies as written; External Secrets skips the conversion under a rewrite (source reading) |
| 3 | One accessor computes the Definitions (templated, delivered keys, closed key set, injected, mounted) | no guard or template decides on its own which keys exist |
| 4 | Precedence is the contract: `dataFrom` in order, `data`, `template.data`; in the container `envFrom`, `config`, the Secret, `env` | External Secrets' merge order (source reading, harness) |
| 5 | A curated `template`: `data` (at least one `{{`) and `mergePolicy` (`Merge` by default, required, always rendered), the chart's labels in `template.metadata.labels`, never `engineVersion` | External Secrets' default `Replace` would drop every other key; labels are no longer copied once a template exists (source reading) |
| 6 | The file mount: `mountPath`, `items`, `defaultMode`, the volume `external-secret` rendered iff mounted, read-only everywhere | a certificate as a file; 0.7.0's path rules reused |
| 7 | `envFrom`: a required boolean, default `true`; `false` requires a reader | the switch must not be turned off silently by a `null` |
| 8 | The schema takes any Secret key; while injected, a guard requires variable names and rejects `Base64`/`Base64URL` decoding, unless templated with `Replace` | the kubelet injects every key (source reading); binary content in a variable can keep a container from starting |
| 9 | `external-secrets.io/v1` (External Secrets 0.16 or later); `data` gains `version` and `decodingStrategy`, and a `null` entry or optional field is absent | the API served since 0.16.0; the null rule per map |
| 10 | A disabled block keeps its keys unchecked by the guards, except an entry's mount of `external-secret` and an `externalSecretKeyRef` | an umbrella switches the block per environment |
| 11 | `env.<NAME>.valueFrom.externalSecretKeyRef: {key}`, ADR-0054 | a hand-written `secretKeyRef` dangles under another release name or alias (measured on 0.6.0) |
| 12 | The e2e: `full`, `job` and `worker` exercise the new keys; the docs: ADR-0053, ADR-0054, README, guides, upgrade notes, roadmap | the first run of External Secrets with these specs is CI's |
| 13 | Autonomous mode: Task 9 pushes and watches CI; the controller merges and releases | the owner's authorization of 2026-10-03 |

## Deviations from the plan

- **Task 3:** the implementer applied code before running RED, then reverted it; RED ran on the unchanged chart and
  matched the plan (28 failed, 21 errored, 908 total, both Helm versions; the reviewer confirmed it independently).
  From Task 4 on, implementers were told to run RED before any change.
- **Task 8:** dispatched while the Task 7 review ran (a ruling above); its review, first folded into the final
  documents lens, was run as a task review after all.
- **Plan review C4:** the alias contract once failed on Helm 4.3.0 in the plan review on a check 0.9.0 does not touch
  (`secretStoreRef.kind null`). It did not reproduce: 17 further runs, 80 runs of that one render, and in the execution
  three runs per Helm version at Task 7 and in the fix wave all passed. Its cause is unknown.
- **The fix wave**, where a ruled fix turned out not to be possible as written, applied the closest true version (each
  with its evidence below, under the findings): one schema message changed beyond its path (D-T1-M4), one Secret-key
  rule kept inline (D-T3-M5), a separate test in place of a second value in a test (M-3), a test without a schema
  change (M-4), and a retitle in place of a lower layer (D-T1-M6).
