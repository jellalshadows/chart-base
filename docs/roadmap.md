# Roadmap to 1.0

The goal is a finished 1.0 of chart-base, validated by the first real domain umbrella that consumes it. The positioning the 1.0 has to earn, and that the comparison matrix in the README must back, is: *the production-safe generic chart for alias-based umbrellas: production defaults on, every integration opt-in, a strict schema, alias-safe, tested end to end in clusters that enforce Pod Security `restricted`*. Listing on Artifact Hub and other promotion come after 1.0.

The differentiators the 1.0 must preserve: alias-safety (charts that are not alias-safe break when aliased twice in one umbrella), a strict schema at every level, Pod Security `restricted` and resilience on by default, `helm.sh/chart` kept out of the pod template, the config checksum computed over `.data` only, Job hooks whose supporting resources are hooks too, and a missing CRD failing the render instead of being skipped.

## Principles

These apply to every release.

- **Integrations are off by default.** Anything that needs another system (Prometheus Operator, KEDA, NetworkPolicy, Gateway API, External Secrets Operator, ...) is activated only with an explicit `enabled: true`.
- **Posture is on by default.** Pod Security `restricted`, PodDisruptionBudget, topology spread, preStop, `progressDeadlineSeconds` and mandatory resource requests. Lowering the posture is explicit, key by key.
- **The contract is curated.** Every new key comes with a schema using `additionalProperties: false`, `required` wherever a `null` would silently change a default, and `fail` guards for cross-key rules. A new key is additive (minor); changing a default, renaming a key or rejecting or changing a value that an earlier release accepted is a breaking change (`feat!`, or `fix!` when it fixes released behaviour, as the first PR of 0.7.0).
- **One workload per alias.** No feature introduces several workloads or several Services per alias, because that would break alias-safety.
- **Every feature ships complete.** helm-unittest tests written test-first (negative cases included), a scenario in `ci/` (or an extension of an existing one), a check in `e2e.sh` against the real system in kind whenever an operator or CRD is installed in the e2e, updated snapshots, rows in the values table, and its documentation in the repository: new ADRs in `docs/adr/` with context, decision, consequences and rejected alternatives, plus updates to this roadmap, to the affected guides and runbooks, and to the summarized decision in the README.
- **Every new CI dependency is pinned and maintained.** Each operator or CRD installed in CI is pinned by version and kept current by Renovate, and the rejected list in [Out of scope](#out-of-scope) is respected.

## Open decisions

- **A chart-wide "a `null` entry means absent" rule** (cut before 1.0 on 2026-11-02; a candidate after it). Today the rule
  holds per map only: in 0.7.0 `configFiles.files`, the content of a map-form file, `resources`, `volumes` and
  `strategy.rollingUpdate` ([ADR-0045](adr/0045-null-in-configfiles-and-resources-is-absent.md), [ADR-0049](adr/0049-volumes-are-a-map-of-typed-entries-mounted-in-the-main-container.md),
  [ADR-0050](adr/0050-existing-claim-on-a-deployment-and-strategy-rollingupdate-null.md)), in 0.8.0 `initContainers` and `sidecars` for optional fields at any depth but inside a list, an env
  variable's `valueFrom` and a probe's `httpGet` or `exec` (a required field such as a mount's `mountPath` stays an error) ([ADR-0051](adr/0051-init-containers-and-sidecars-are-two-maps-in-one-start-order.md)), in 0.9.0 `externalSecret.data` (an entry, or an optional field of one) and `externalSecret.template.data` ([ADR-0053](adr/0053-externalsecret-datafrom-template-files-and-an-envfrom-switch.md)), in 0.10.0 `keda.triggers` (an entry, an optional field or a metadata key of one; [ADR-0056](adr/0056-keda-scaledobject-a-curated-block-with-a-triggers-map.md)), in 0.11.0 `extraObjects` (an entry, or a field of one at any depth through maps; a list kept as written; [ADR-0057](adr/0057-common-labels-and-annotations-service-annotations-and-extraobjects.md)). The main container's `env.<NAME>: null` would give 0.9.0's `externalSecretKeyRef` an overlay remedy in an environment that disables the ExternalSecret ([ADR-0054](adr/0054-env-externalsecretkeyref-references-the-components-own-secret.md)). What stays without it once the maps of 0.7.0 to 0.10.0 are converted: one
  entry of a typed map (`config`, the main container's `env`, `podLabels`, `podAnnotations`, `ingress.annotations`,
  `serviceAccount.annotations`, `metrics.labels`, `prometheusRule.labels`, `nodeSelector`,
  `networkPolicy.egress.dns.podSelector`) and an optional member of a closed object (`lifecycle.<hook>`,
  `strategy.rollingUpdate.maxSurge` and `.maxUnavailable`, `dnsConfig.nameservers`, `.searches`, `.options`), schema errors today; a key inside a
  pass-through object (`probes.<probe>.<key>`, `affinity.<key>`, the keys of `podSecurityContext` and
  `securityContext` that `values.yaml` does not define), rendered as `null` today, so converting it changes the
  manifest; `httpRoute.matches`; one entry of `commonLabels`, `commonAnnotations` or `service.annotations`. Converting a map
  converts its template readers and guards with
  it. 0.12.0 converted one of those pass-through objects, the main container's probes: a `null` field is absent there
  now, as in a sidecar's ([ADR-0059](adr/0059-one-probe-contract-for-every-container.md)).

- **Follow-ups of 0.8.0** ([ADR-0051](adr/0051-init-containers-and-sidecars-are-two-maps-in-one-start-order.md)), each additive: a per-entry `automountToken: false` (today every
  init container and sidecar gets the token when the pod does); an entry-level `config` for literal variables (the
  first real case: cloud-sql-proxy's `CSQL_PROXY_*` settings, today passed in `args`); `lifecycle` on an entry; a
  sidecar port exposed in the Service.
- **Follow-ups of 0.9.0** ([ADR-0053](adr/0053-externalsecret-datafrom-template-files-and-an-envfrom-switch.md), [ADR-0054](adr/0054-env-externalsecretkeyref-references-the-components-own-secret.md)), each additive: `dataFrom` `find`, `sourceRef`
  and `metadataPolicy`; `template.templateFrom`, a Secret `type` and custom delimiters; `refreshPolicy`,
  `deletionPolicy`, `immutable`, `creationPolicy`; a second mount of the Secret in the main container (a `mounts`
  map); `optional` on `externalSecretKeyRef`. Each relaxes a rule or adds a key: decoded content behind `envFrom` and a
  `template.data` value without a template action fail today and can be accepted later without a breaking change, but
  not the reverse.
- **Follow-ups of 0.10.0** ([ADR-0055](adr/0055-hpa-behavior-and-metrics-are-validated-pass-throughs.md), [ADR-0056](adr/0056-keda-scaledobject-a-curated-block-with-a-triggers-map.md)), each additive (the opt-in handover
  from the chart's HPA to KEDA, O1 of the 0.10.0 design, shipped in 1.1.0 as `autoscaling.kedaHandover`): `tolerance` once the floor reaches Kubernetes 1.35; a
  chart-rendered TriggerAuthentication and a ScaledJob; `autoscaling.behavior` converted to "a `null` means absent"; a

- **Literal variables for an init container** (the first real umbrella's finding G4): the entry-level `config` of the

### Taken for the 1.0 contract (0.12.0)

The decisions that this section held for the contract freeze were taken on 2026-11-17 and ship in 0.12.0
([upgrade guide](upgrading.md#011x--0120)):

- **`ingress.className: null`**, which rendered an Ingress without a class: the class is required while the Ingress is
  enabled, `null` included; "no class" on purpose was rejected, because it hands the choice to a fact of the cluster
  that the values do not show ([ADR-0061](adr/0061-reserved-metadata-keys-and-a-required-ingress-class.md)).
- **One rule for the ServiceAccount token directory as a mount path**: `configFiles.mountPath` now rejects it whether
  or not the token is mounted, as `volumes` and every later mount did
  ([ADR-0060](adr/0060-the-main-container-takes-the-entries-checks-and-one-token-directory-rule.md)).
- **A per-volume Reloader opt-out**: not added. The first real umbrella mounts no ConfigMap or Secret volume and did not
  ask; adding the key later is additive ([ADR-0058](adr/0058-the-1-0-contract-and-how-it-stays-frozen.md)).
- **`pdb.minAvailable` against the autoscaler's minimum**: a guard in all three modes, fixed `replicas`, the HPA and
  KEDA, at the replica floor (`max(keda.minReplicaCount, 1)` with KEDA); a budget that blocks drains on purpose goes in
  `extraObjects` ([ADR-0062](adr/0062-a-pdb-never-blocks-a-drain-at-the-replica-floor.md)).
- **The checks that rejected values that rendered**: all of them. A `lifecycle` port name must be in `ports`, a
  main-container `subPath` must name an `items` path, and UID 0 with `runAsNonRoot: true` fails on the main container
  too ([ADR-0060](adr/0060-the-main-container-takes-the-entries-checks-and-one-token-directory-rule.md)). The main
  container's probes are closed like a sidecar's, so the chart has one probe contract
  ([ADR-0059](adr/0059-one-probe-contract-for-every-container.md)). `podLabels`, `podAnnotations`,
  `ingress.annotations` and `serviceAccount.annotations` reject the chart's and Helm's keys
  ([ADR-0061](adr/0061-reserved-metadata-keys-and-a-required-ingress-class.md)).
- **`app.kubernetes.io/component`** (the first real umbrella's finding G6): the chart wrote the workload type there; it no
  longer writes the key, which is the consumer's ([ADR-0063](adr/0063-the-chart-does-not-write-app-kubernetes-io-component.md)).

## 1.0.0 criteria

1. All feature releases above (0.2.0 to 0.11.0) and the cosign signing step are published, each with its e2e green on Kubernetes 1.33 and 1.37 (or the supported versions current at that time). **Met:** 0.11.0 was published on 2026-11-03.
2. The chart is validated by the first real domain umbrella, deployed with helmfile. Whatever that use reveals is fixed before 1.0. **Met on 2026-11-17:** `jellalshadows/domain-boutique`, CI green on kind 1.33 and 1.37. Its findings are answered in 0.12.0: two by contract changes (the closed probes, the component label), four by documentation (a sibling's address, umbrella-wide defaults, a Secret on the command line, the version label under a digest), one by the umbrella lifecycle check in CI (CronJob and Job aliases), and one deferred as an additive follow-up (literal variables for an init container).
3. The contract is frozen: selector labels and key names. From 1.0 on, only additive changes (`feat:`) or explicit majors. **Frozen by 0.12.0:** [ADR-0058](adr/0058-the-1-0-contract-and-how-it-stays-frozen.md) lists the contract, `tests/contract_test.yaml` pins the names, selectors and label keys, and CI fails on a removed or renamed values key (`contract-keys.sh`).
4. The README carries a comparison matrix (dated, with the versions checked) that backs the positioning above, re-verified against the current versions of the other charts before it is published. **Met:** [How it compares](../README.md#how-it-compares), checked on 2026-11-17.

1.0.0 changes no contract. It is cut after a validation campaign on kind against the published 0.12.0; a defect that the
campaign finds ships first as a `fix:` 0.12.x. **Met on 2026-11-17:** scenarios C1-C10 on Kubernetes 1.33.12 and 1.37.0,
each with Helm 3.22.0 and 4.3.0, found no defect of the chart. The one failing check was a race of `e2e.sh` on Helm 3,
fixed in #31, so no 0.12.x was needed.

## Out of scope

Rejected features, with the reason:

- **DaemonSet.** It conflicts with Pod Security `restricted`.
- **SealedSecrets, plain Secrets and SecretProviderClass.** They would add a second path for secrets next to External Secrets Operator.
- **cert-manager Certificate.** TLS is terminated at the Gateway.
- **ClusterRole and ClusterRoleBinding.** Cluster-scoped RBAC breaks multi-tenancy.
- **A chart-created PersistentVolumeClaim for Deployments.** It causes Multi-Attach errors; use an `ephemeral` volume, or a StatefulSet outside this chart. An existing claim can be mounted (`volumes`, 0.7.0); on a Deployment, one declared `ReadWriteOnce` requires one pod at a time ([ADR-0050](adr/0050-existing-claim-on-a-deployment-and-strategy-rollingupdate-null.md)).
- **Several workloads, or non-native containers, per alias.** It breaks the one-workload-per-alias model.
- **Helm tests.** The e2e already validates the chart and Argo CD does not run them.
- **`nameOverride` and `fullnameOverride`.** See [ADR-0009](adr/0009-no-name-overrides.md).
- **Gating on `.Capabilities`.** See [ADR-0012](adr/0012-no-capabilities-gating.md).
- **Resource presets.** See [ADR-0014](adr/0014-resource-requests-required.md).
- **`diagnosticMode`.** `kubectl debug` already covers diagnosis.

Only with real demand, and only after 1.0: VPA, Argo Rollouts, KEDA ScaledJob, TLS/TCP/UDP Routes and ListenerSet, and the
work cut before 1.0 (below).

## Cut before 1.0

On 2026-11-02 the owner cut the roadmap to what any company needs from a generic application chart; the rest waits
for a real umbrella to ask for it, after 1.0. `extraObjects` (0.11.0) lets a consumer render what the chart does not
offer in the meantime.

- **GRPCRoute, HTTPRoute rules and `ports[].appProtocol`** (the former 0.11.0), and the stricter checks of the existing
  `httpRoute` fields that made it breaking: the API server already rejects those values at install.
- **A chart-wide "a `null` entry means absent" rule** (part of the 0.12.0 planned before the cut; the 0.12.0 that
  shipped converts only the main container's probes; see [Open decisions](#open-decisions)).
- **The StatefulSet workload type** (the former 0.13.0): stateful systems usually run under their own operators.
- **Closing the existing label and annotation maps** to the chart's and Helm's own keys (part of the 0.12.0 planned
  before the cut): breaking, so it joined the checks of the 1.0 contract freeze, and 0.12.0 takes it
  ([ADR-0061](adr/0061-reserved-metadata-keys-and-a-required-ingress-class.md)).

## How each release is made

1. **Short design.** A short design review of the exact contract of the release (keys, defaults, guards, what the e2e proves), approved by the owner. The open decisions marked above are taken here.
2. **Verified plan.** An implementation plan with the complete code, prototyped and verified beforehand.
3. **Implementation with reviews.** The plan is implemented task by task, with a review of every step and a final review of the whole branch.
4. **Pull request.** A PR with green CI, including the real kind e2e, is merged; release-please then opens the release PR.
5. **Release.** The owner merges the release PR, and the publish is verified. The status of the release in this roadmap is updated as part of that release.
