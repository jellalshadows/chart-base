# chart-base

Generic Helm chart for any workload, consumed as an aliased dependency.

`chart-base` is **one** Helm application chart, with **one** version, that deploys **any** workload:
an HTTP API, a worker without a Service, a CronJob or a Job. Services never write templates:
a business-domain umbrella chart declares `chart-base` once per component, each with a different
`alias`, and configures every component under its alias.

## Quick start

A domain umbrella (`vending`) with three components. **All aliases must use the same `chart-base` version.**

```yaml
# vending/Chart.yaml
apiVersion: v2
name: vending
version: 0.1.0
dependencies:
  - name: chart-base
    version: 0.1.0
    repository: oci://ghcr.io/jellalshadows/charts
    alias: sales
    condition: sales.enabled
  - name: chart-base
    version: 0.1.0
    repository: oci://ghcr.io/jellalshadows/charts
    alias: machines
    condition: machines.enabled
  - name: chart-base
    version: 0.1.0
    repository: oci://ghcr.io/jellalshadows/charts
    alias: front-web
    condition: front-web.enabled
```

```yaml
# vending/values.yaml — every component is configured under its alias
sales:
  image:
    repository: ghcr.io/acme/sales
    tag: "1.4.2"
  resources:
    requests: {cpu: 250m, memory: 512Mi}
```

```bash
helm dependency update vending/     # no `helm repo add` needed for OCI
helm template vending vending/      # renders vending-sales, vending-machines, vending-front-web
```

Every resource is named `<release>-<alias>` (e.g. `vending-sales`).

## Recipes

### HTTP API (Spring Boot) with HTTPRoute, ExternalSecret and application.yaml

```yaml
sales:
  image: {repository: ghcr.io/acme/sales, tag: "1.4.2"}
  resources:
    requests: {cpu: 250m, memory: 512Mi}
    limits: {memory: 1Gi}
  config:                                   # env vars -> ConfigMap vending-sales-env -> envFrom
    SPRING_PROFILES_ACTIVE: prod
    SPRING_CONFIG_ADDITIONAL_LOCATION: "optional:file:/config/"
  configFiles:                              # files -> ConfigMap vending-sales-files -> /config
    files:
      application.yaml:                     # a map: mergeable per environment
        spring:
          datasource:
            url: jdbc:postgresql://db:5432/sales
            password: ${DB_PASSWORD}        # placeholder resolved from the env var below
  externalSecret:                           # ESO -> Secret vending-sales-secrets -> envFrom
    enabled: true
    secretStoreRef: {kind: ClusterSecretStore, name: gcp-sm}
    data:
      DB_PASSWORD: {key: sales-db-password}
  probes:
    readiness:
      httpGet: {path: /actuator/health/readiness, port: http}
    liveness:
      httpGet: {path: /actuator/health/liveness, port: http}
  autoscaling:
    enabled: true
  httpRoute:
    enabled: true
    parentRefs: [{name: platform-gw, namespace: gateway, sectionName: https}]
    hostnames: [sales.example.com]
```

`spring.config.additional-location` adds `/config/` on top of the `application.yaml` packaged in the jar
and **overrides** it; it must arrive as an environment variable, and directories end with `/`
([Spring Boot docs](https://docs.spring.io/spring-boot/reference/features/external-config.html)).
Never put secret values in `configFiles`: use `${VAR}` placeholders fed by `externalSecret`.

### Worker (e.g. a Kafka consumer)

```yaml
machines-consumer:
  image: {repository: ghcr.io/acme/machines, tag: "2.0.1"}
  args: ["--mode=consumer"]
  ports: []
  service:
    enabled: false
  resources:
    requests: {cpu: 100m, memory: 256Mi}
```

### CronJob

```yaml
cleanup:
  workload: {type: cronjob}
  image: {repository: ghcr.io/acme/sales, tag: "1.4.2"}
  command: ["java", "-jar", "app.jar", "--task=cleanup"]
  ports: []
  resources:
    requests: {cpu: 100m, memory: 256Mi}
  cronjob:
    schedule: "0 3 * * *"
    timeZone: Europe/Madrid
```

### Job (database migrations before every deploy)

```yaml
sales-migrations:
  workload: {type: job}
  image: {repository: ghcr.io/acme/sales-migrations, tag: "1.4.2"}
  ports: []
  resources:
    requests: {cpu: 100m, memory: 256Mi}
  externalSecret:
    enabled: true
    secretStoreRef: {kind: ClusterSecretStore, name: gcp-sm}
    data:
      DB_PASSWORD: {key: sales-db-password}
  job:
    phase: pre-deploy        # runs and must succeed before anything in the release is updated
```

## Design decisions

Each decision lists **why** and the **rejected alternative**. Facts were verified on 2026-09-27 against
primary sources (Helm v4.3.0/v3.22.0 source code, official docs) and local renders.

1. **Application chart consumed through aliases.** Helm validates a subchart's `values.schema.json`
   against the values under its alias, so every component is validated; services write no templates.
   *Rejected:* a library chart, whose schema never validates the consumer's values.
2. **The repository is the chart (at the root).** One artifact; `exclude-paths` keeps CI/test commits
   from releasing. *Rejected:* `charts/chart-base/`, a multi-chart convention.
3. **OCI on GHCR, public and free.** No `helm repo add`; the package is linked to this repository.
   *Rejected:* an HTTP Helm repository on GitHub Pages.
4. **Env vars in a ConfigMap, secrets through ExternalSecret into a Secret, both via `envFrom`.**
   Kubernetes: *"ConfigMap does not provide secrecy or encryption"*; Secrets get stricter RBAC.
   *Rejected:* secrets in a ConfigMap (possible with ESO only behind `--unsafe-allow-generic-targets`).
5. **`configFiles` accepts a string or a map.** A map merges per environment (`null` deletes a key);
   a string is written verbatim. Map values go through YAML: quote ambiguous scalars
   (`"on"`, `"1.10"`, `"0755"`). *Rejected:* strings only (no per-environment merge).
6. **Config changes roll pods through a checksum; Secret rotation through Reloader.** Config changes
   happen inside the deploy, so Helm sees a broken config and rolls back; Secrets change outside the
   deploy, when ESO syncs. *Rejected:* Reloader for everything (Helm would report success before the
   restart, and the next deploy of the domain would fail on someone else's broken component).
7. **`workload.type: job` is a Helm hook (`job.phase`).** A Job pod template is immutable, so a plain
   Job fails on the second deploy with `field is immutable`. Its ServiceAccount, ConfigMaps and
   ExternalSecret are hooks too (weight `-10`) so they exist, with the new content, before the Job.
   *Rejected:* a plain Job; a Job named after the release revision (no ordering, not blocking).
8. **Names are always `<release>-<alias>`, and too-long names fail.** Uniqueness is guaranteed; names
   are never truncated (truncation can make two components collide). Limits: 63 characters, 52 for
   CronJobs. *Rejected:* the `helm create` helper (`contains` shortcut + truncation).
9. **No `nameOverride`/`fullnameOverride`.** Two aliases with the same override render duplicate names
   that neither `helm lint` nor `helm template` detect. The alias is the identity.
10. **`helm.sh/chart` is never a pod label.** Otherwise bumping `chart-base` would restart every pod of
    the domain without any real change.
11. **Strict draft-07 schema with reserved `global` and `enabled`.** Typos fail instead of being ignored;
    draft-07 works on every Helm 3/4 release. Helm always injects `global`, and `condition: <alias>.enabled`
    puts `enabled` under the alias. *Rejected:* draft 2020-12; a permissive schema.
12. **No `.Capabilities` gating for CRD kinds.** Helm builds every object before creating anything, so a
    missing CRD already fails the release cleanly. *Rejected:* a gate plus an escape flag.
13. **Secure by default:** Pod Security Standards `restricted`, read-only root filesystem (with `/tmp`
    as an emptyDir), numeric UID 65532, no ServiceAccount token.
14. **`resources.requests` are required.** HPA utilization and scheduling depend on them.
15. **PDB and topology spread on by default.** `maxUnavailable: 1` still lets a single-replica pod be
    evicted, and `AlwaysAllow` lets drains evict pods that are not Ready.
16. **HTTPRoute first, Ingress optional and controller-neutral.** ingress-nginx was retired in March 2026
    and the Ingress API is frozen. *Rejected:* Ingress with nginx annotations by default.
17. **`progressDeadlineSeconds: 240`.** A broken component fails before Helm's 300s timeout, with the
    real cause. *Rejected:* the Kubernetes default (600s).
18. **`kubeVersion: ">=1.33.0-0"` plus a template guard.** 1.33 is supported by EKS/GKE/AKS into 2027;
    `-0` accepts provider suffixes like `v1.33.5-eks-x`; Helm does not check a subchart's `kubeVersion`.
19. **Helm 4 first, Helm 3.22 still tested.** Helm 3 only receives security fixes until 2027-02-10.
20. **release-please v5 and publishing in the same workflow, with an overwrite guard.** Tags created by
    `GITHUB_TOKEN` do not trigger other workflows, and GHCR tags are mutable while `Chart.lock` stores no
    digest. *Rejected:* a PAT plus `workflow_run` with a "latest tag" heuristic.
21. **release-please uses a GitHub App token.** CI runs on the Release PR automatically; tokens live 1h.
22. **Provenance with `actions/attest`, no cosign yet.** Verifiable with `gh`; fewer moving parts on GHCR.
23. **No chart-testing (`ct`).** Its last release predates Helm 4 and its version-bump check conflicts with
    release-please. Plain Helm and kind instead.
24. **Renovate.** It updates action SHAs *and* tool versions (Helm, kubeconform, kind images).
25. **Generated README.** The values table cannot drift from `values.yaml`.

## Versioning and releases

- Conventional commits, squash-merged with the PR title as the commit message.
- [release-please](https://github.com/googleapis/release-please) keeps a Release PR open with the next
  version and `CHANGELOG.md`. Merging it tags `vX.Y.Z` and publishes
  `oci://ghcr.io/jellalshadows/charts/chart-base:X.Y.Z`. Nothing else ever publishes.
- Before 1.0: `fix:` → patch, `feat:` → minor, `feat!:` → minor. 1.0.0 will be declared on purpose,
  and from then on the selector labels are frozen forever.
- An existing version is never overwritten: the publish job fails if the tag already exists.
- Verify where a version was built:

```bash
gh attestation verify oci://ghcr.io/jellalshadows/charts/chart-base:X.Y.Z --repo jellalshadows/chart-base
```

## Rules for consumers

- **One `chart-base` version per umbrella.** With mixed versions Helm's named templates collide (one
  version renders all aliases) and `helm package` drops one version.
- **Aliases are lowercase kebab-case** (`front-web`), and `<release>-<alias>` must fit in 63 characters
  (52 for CronJobs). Renaming an alias deletes and recreates its objects.
- **Toggle components with a real boolean**: `sales.enabled: false`. A string `"false"` is ignored.
- **Install [Stakater Reloader](https://github.com/stakater/Reloader)** with `reloadStrategy: annotations`
  for Secret rotation to reach the pods.
- **HTTPRoute** needs a Gateway whose listener allows routes from the application namespace
  (`allowedRoutes`); the default only allows the Gateway's own namespace.
- **Turning on `autoscaling` for a running component** removes `spec.replicas`: Kubernetes scales it to 1
  once, then the HPA scales it back up.
- **Quote image tags** (`tag: "1.10"`): the schema only accepts strings, so an unquoted `1.10` fails
  instead of silently becoming `1.1`.

## Development

Local loop (no Docker needed): [helm-unittest](https://github.com/helm-unittest/helm-unittest).

```bash
helm unittest .                          # every template is born from a failing test
helm unittest . -u                       # update tests/__snapshot__ after an intended change
helm lint --strict . -f ci/full-values.yaml
```

CI (`.github/workflows/ci.yaml`) runs the unit tests, `helm lint`/`helm template` + kubeconform on
Helm 3.22 and 4.3, the alias contract (`.github/scripts/alias-contract.sh`), a real install on kind
(Kubernetes 1.33 and 1.37) in a namespace that enforces Pod Security `restricted`, this README drift
check, the PR title check and workflow linting (actionlint + zizmor).
